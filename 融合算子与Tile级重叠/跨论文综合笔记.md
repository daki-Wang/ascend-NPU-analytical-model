# MoE / NPU 计算通信融合与性能建模：跨论文综合笔记

整理日期：2026-11-03。研究主题：**NPU 卡上 MoE 场景计算通信融合算子的性能模型与优化**。

## 阅读范围与判定口径

本笔记基于 `MoE_NPU课题相关论文` 下的 **32 份 PDF、31 项研究**及已有逐篇笔记。共享缓存模型有早期稿与 IEEE Access 期刊版，分别列证据，不作为两项独立验证。GCoM 也纳入原文核查。下文 `[Pxx]` 对应末尾逐篇引文条目和原 PDF 链接；页码均为**本地 PDF 文件页序**，含封面，非期刊印刷页码。

这里的“共识”是本资料集内多项工作的重复证据，并不意味着所有硬件和工作负载上都成立。“分歧”区分**相反的实验现象**、**设计取舍不同**和**指标不能比较**；没有相同硬件、代码与负载下的直接对照时，不声称某篇推翻另一篇。“空白”指这批论文中仍未系统验证的问题，不能据此断言整个领域无人研究。

证据层级分开记录：Ascend 实机算子/训练结果；NVIDIA/AMD GPU 实机结果；抽象 NPU/NDP 模拟或 RTL 验证；CPU 缓存分析；以及作者提出但尚未实测的扩展。**DA-MoE 的融合主要是专家计算 kernel 的融合，它不直接验证跨卡通信计算融合；LENS 也不是 MoE 融合算子模型。**

## 一、共识区

### 1. 已反复验证的结论

| 结论 | 重复证据及实验边界 | 对本课题的含义 |
|---|---|---|
| **C1：以 tile/split 的数据就绪依赖替代整算子屏障，可以缩短暴露通信时间。** | COMET 的共享 tensor 拆分、Tile-level Signaling 的 producer-consumer 通知、TileLink 的原语编译、FlashMoE 的持久 kernel，以及 HyperParallel-MoE 的 AIC/AIV taskflow，分别在 GPU 或 Ascend 上展示收益。[P23 §3–5；P25 §3–4；P27 §3–7；P24 §3–4；P01 §4–6] | 模型应保留“哪个 tile 到达后哪个计算可以启动”，不能仅把完整 All-to-All 与完整 GMM 的耗时各算一次。重复成立的是细化依赖的价值，尚不是特定 tile 尺寸或固定加速比。 |
| **C2：计算、通信的独立最快配置，通常不是融合流水整体的最快配置。** | COMET 与 Analytical Resource Management 优化通信/计算 CTA 配比；Weave 根据路由选择 SM 切分；Tile-level Signaling 中通信 consumer 过少反而比串行基线更慢。SwiftEP 则通过减少通信 SM 占用改善与计算并发时的表现。[P23 §3.2、5.4；P18 §III–IV；P19 §3–5；P25 §4.3.4；P28 §8] | 目标函数应是依赖约束下的 makespan，同时计入计算效率、通信推进速率、共享带宽竞争和资源预留。Ascend 要重新定义 AIC/AIV、MTE 与队列的资源约束，不能照搬 SM 数。 |
| **C3：更细的切分存在收益与成本的交叉点。** | HyperParallel-MoE 在较大工作集上受益，但小工作集可能轻微变慢；Weave 的 GEMM chunking 会降低吞吐；MPMoE 显示过细微批次切分增加开销并影响硬件利用率；Tile-level Signaling 的小 hidden dimension 案例无法超过部分高效基线。[P01 §6；P19 §4–5；P22 §III–V；P25 §4.2.1] | tile/segment/split 数必须作为优化变量。需同时计入流水 fill/drain、同步、任务管理、padding 和 kernel 效率下降，而非假设粒度越细越好。 |
| **C4：总 token 数不足以完整描述 MoE 工作量，专家分布和最慢 rank/执行单元会影响延迟。** | DA-MoE 在相同 token bucket 内发现最优 kernel 随分布改变；Weave 以实际路由选择资源；COMET 测得偏斜加剧时各系统延迟上升；DynaNDE 将激活专家及驻留状态用于调度。AMALI/SynPerf 对 warp/SM 不均衡提供了不同层级的旁证。[P03 §III–V；P19 §2–5；P23 §5.4；P20 §3–5；P15 §III–IV；P16 §IV] | 需要 expert-token histogram、每 rank 流量和 tile 数，并显式保留长尾。GPU 单卡的分布适配证据不能单独证明 Ascend 多卡上的同等收益。 |
| **C5：性能模型要表达目标硬件的实际执行机制，并用测量校准。** | NPUMeter/AdaptCore 建模 Ascend 的搬运、Cube 流水与 buffer 约束；MDM 补入 MSHR 和 NoC/DRAM 排队；AMALI 补入 tensor-core 指令、启动相关开销与 warp 指令不均衡；SynPerf 用任务调度和资源特征连接解析与学习模型。[P08 §4–6；P05 §4–6；P14 §III–VI；P15 §III–VI；P16 §IV–VI] | FLOPs/峰值算力或 bytes/峰值带宽可作下界与粗筛，但不足以单独预测融合算子的实际关键路径。硬件参数、形状效率和竞争项需要分别校准。 |
| **C6：缓存、buffer 布局和冗余搬运会改变重叠效果。** | HyperParallel-MoE 的交错顺序改变 L2 复用；UniEP 说明 cache contention 导致预测偏乐观；TileSight 将 reuse distance 放入 tile 模型；SwiftEP 通过 buffer fusion 去除复制，但朴素融合也会引入 RNIC 地址转换问题。CPU 缓存论文从另一架构证明共享/一致性会改变 miss 预测。[P01 §6；P02 §6.2；P09 §3.5、7；P28 §4–8；P12–P13] | 需要区分逻辑通信量、真实链路流量和设备内部搬运量；只减少一个计数不保证总时延下降。CPU 缓存公式仅作方法参考，不能直接作为 NPU 参数。 |
| **C7：离线搜索、少量 profiling 与低成本在线决策的组合反复出现。** | AdaptCore 用离线配置与 TilingKey；UniEP 按 bucket 缓存搜索结果；DA-MoE 离线调优 exemplar、在线匹配；Analytical Resource Management 在 launch 前解析选配；LENS 用少量 bucket E2E 测量支撑搜索。[P05 §5；P02 §4、6.2；P03 §IV–V；P18 §III–IV；P04 §4–5] | 可借鉴的是“减少在线搜索成本”，而不是静态或动态方案已决出普遍胜者。决策收益必须扣除统计、查表、模型求解和同步时间。 |
| **C8：算子级优化不等于同倍数的完整模型收益。** | HyperParallel-MoE 的 MoE-FFN 收益高于完整训练 step；Weave 的 layer 收益高于端到端；Analytical Resource Management 分别报告算子、post-router layer、完整模型 prefill；TileLink 和 Tile-level Signaling 也区分层内与模型结果。[P01 §5；P19 §5；P18 §IV、VI；P27 §7；P25 §4] | 至少分别报告 fused operator、MoE layer、训练 step 或服务请求三个层级。不能用局部 hidden communication 百分比替代端到端收益。 |

这些证据并非全都独立：Analytical Resource Management 直接建立在 COMET 实现上；多项系统共用 NVIDIA 通信栈；共享缓存两版来自同一研究。因此“多篇支持”不应被理解为同等数量的独立复现。

## 二、分歧区

### D1. 静态调度更快，还是运行时路由感知更快？——设计取舍不同，尚非同条件互相否定

**相反表象。** HyperParallel-MoE 在 Ascend 训练任务中发现动态调度的逐 task 成本明显高于静态执行，选择离线 SSC；DA-MoE 与 Weave 则把路由结果用于在线 kernel/资源选择并取得收益。[P01 §6、PDF p.15；P03 §V–VI、pp.9–11；P19 §3–5]

**可能原因。** 场景上，前者是可预知算子图和主导 shape bucket 的训练，后两者强调推理路由变化；方法上，逐 tile 设备调度、每层选择资源、每次 graph 选择 kernel 是不同频率的决策；硬件上，AIV task dispatch、CUDA conditional graph 和 H100 持久 kernel 的成本不同。不能直接比较“每 task 2.36 μs”和“整条 selector 路径约 14 μs”。

**需要的判别实验。** 在同一 Ascend 实现上固定 kernel 集合，比较静态、token-bucket、路由感知三种选择；扫 token 数、偏斜、EP 与路由稳定性，单列采集统计、选择和执行成本。在线收益须大于额外决策成本；这一阈值尚无本资料集支持的跨平台常数。

### D2. 细粒度融合带来加速，还是可能变慢？——资料中确有正负结果，条件不同

**正证据。** COMET、FlashMoE、HyperParallel-MoE、TileLink 在各自实验覆盖范围展示加速。**反例。** HyperParallel-MoE 的小工作集交错有轻微 slowdown；Tile-level Signaling 在 M-Trans-xl 上稍落后于 Tutel/Megatron 的部分实现，作者关联到 hidden dimension 较小、通信可隐藏量少；其 consumer CTA 仅为 2 时在所有测试 shape/router 上都慢于基线，最差达基线时延的 1.91 倍。[P01 §6；P25 §4.2.1、4.3.4，pp.7–8]

**原因线索。** 有用工作量变小而通知/调度成本不同比例下降；通信资源不足产生背压；过度 chunking 降低 GEMM 效率。Weave 观察到 chunk 数为 8 时 GEMM 有效吞吐下降约 27%，进一步否定“切得越细越好”的无条件版本。[P19 §4–5]

**本课题应检验。** 预测并实测“融合相对串行开始获益”的边界；保留小 token、小 hidden、低 EP 等负例，不仅报告最佳加速点。

### D3. CPU 应移出关键路径，还是可以提供高性能通信？——控制内容和可用网络能力不同

FlashMoE/UniEP/HyperParallel-MoE 减少 host 管理 kernel 或 collective 的同步；UEP 则采用 CPU proxy，并在不同 GPU/NIC 上展示可移植性与性能。UEP 报告 proxy 约 3–5 μs，相对于其被测 LL/HT 通信规模较小。[P24 §3；P02 §3；P01 §4；P29 §3–6、PDF p.14]

这不构成“CPU 一定慢/一定快”的直接矛盾：CPU 发起整轮同步，与 GPU 产生 token 级请求、CPU proxy 驱动异步网络，是不同路径；IBGDA 可用性、NIC 顺序语义、CPU 线程数和消息率也不同。该结果不能外推为 NPU 上的几微秒 tile 同步也可无代价经过 CPU。应测控制粒度和请求率，区分设备内事件与跨节点传输控制。

### D4. 减少拷贝、使用卸载引擎是否必然更快？——同一论文中就有反例

SwiftEP 的完整 buffer fusion/TMA 方案有效，但单独 RDMA buffer fusion 可显著降低带宽；朴素 TMA reduce 也会因 shared-memory 容量不足而变慢，需 QP 并行、WQE 合并、动态 shared memory 和传输重叠共同解决。[P28 §8.2–8.3，pp.11–12]

原因是减少 SM 复制后，瓶颈转移到 RNIC 地址翻译、小片段处理或 TMA 工作空间，逻辑流量下降不等于事务开销下降。对 Ascend 的对应问题是：搬运卸载后，MTE、UB/L1、事件或共享 L2 是否成为新瓶颈。这是需要实验的迁移假设，不是 SwiftEP 已验证的 NPU 结论。

### D5. 不规则 MoE 通信适合交换机卸载吗？——这里存在值得正面检验的可行性分歧

SwiftEP 认为 token multicast/reduce 的稀疏、不对称、动态子集特征使现有对称 collective 的网络内卸载不实用。[P28 §10，p.13] INC-MoE 则把 dispatch/combine 表达为 in-network AllGather/ReduceScatter，以 band 流水与专家计算重叠，原型在模拟四节点、每 rank 100 Gbps 的环境中获得 prefill 收益。[P26 §3、5]

**关键差异。** 两者的通信表示、payload 去重/广播范围、交换机所需语义、网络上下行使用方式和部署假设不同；INC-MoE 的 INC switch 是 accelerator emulator，不能据此认定真实交换机的吞吐、精度、容量和控制面问题已解决。相反，也不能用 SwiftEP 对现有卸载限制的判断，直接否定重新表达 collective 的可能性。

**公平判别。** 用同一 expert histogram、top-k、rank 拓扑和 per-rank 带宽，对比稀疏 token All-to-All 与密集/分带 AG+RS 的真实字节量、端点资源、交换机状态、fill/drain 及端到端收益；必须补真实交换机验证。

### D6. 某模型只有百分之几误差，另一模型有十几个百分点，是否说明方法更优？——多数属于不可比指标

| 论文与报告值 | 预测对象和 ground truth | 不可混用的原因 |
|---|---|---|
| LENS：整体平均误差 2.15% | 经过目标 NPU bucket E2E profiling 的推理时延 | 并非无需目标硬件测量的算子泛化精度。[P04 §5] |
| UniEP：三类配置平均约 3.8% | 特定 Hopper overlap 配置；作者承认 cache contention 导致偏乐观 | 与普通串行 kernel、完整请求不是同一对象。[P02 §6.2] |
| TileSight：单 GPU pooled MAPE 12.35%；融合分布式 kernel wMAPE 16.18% | 多类 tile 程序与不同硬件/分布式 kernel | pooled MAPE 与 wMAPE 的权重不同，长短 kernel 影响不同。[P09 §5] |
| MDM：模拟对照平均 13.9%，GTX1080 实机平均 40% | 不同 trace/参考设备条件下的 IPC | 仿真拟合与实机精度必须分开。[P14 §V–VI] |
| AMALI：Llama3-8B 高频长 kernel 集合 MAPE 23.59% | NCU 实测周期，含 GEMM 与 element-wise | prefill/decode 的分项误差另有差异。[P15 §VI] |
| SynPerf：正文已见/未见 GPU kernel MAPE 6.0%/11.5% | 训练硬件与未见硬件上的 kernel 预测 | 需区分数据划分、kernel 类型和端到端汇总。[P16 §VI] |
| ONNXim：Gemmini RTL 核心校验平均误差 0.61% | 排除 softmax、normalization、skip connection 的核心校验 | 不是全 NPU 系统、不是跨卡 MoE 精度。[P11 §III-C] |

LENS 认为商业 NPU 黑盒编译器与 bucketing 令逐算子相加失真；NPUMeter/AdaptCore 则在可分析的 Ascend 算子范围内取得较好效果。两者预测边界不同，不能据此得出“解析模型不可行”或“E2E 只需相加”。

**建议统一比较口径。** 同一测试集、同一计时边界、同一目标硬件可见程度；报告未见 shape/未见分布/未见硬件三类测试、MAPE 与加权误差、候选配置 regret、采样和求解成本。对优化而言，排序正确和选配 regret 与绝对误差同样重要。

### D7. 路由均衡近似影响很小，还是路由偏斜必须显式建模？——测量尺度和扰动范围不同

SimAI 在 EP 通信仿真中采用 balanced distribution，并称对其仿真结果影响很小；DA-MoE、Weave 与 COMET 展示分布变化对局部 kernel、资源选择或 layer 延迟的影响。[P17 §3.4，p.8；P03 §V；P19 §2–5；P23 §5.4]

SimAI 的训练 iteration 级聚合验证没有证明任意偏斜下均衡近似都安全；DA-MoE 在小 token 推理下的 kernel 选择敏感性，也不能证明训练 iteration 必有同等变化。需固定总通信量，分别制造 expert skew、rank skew、链路热点，观察局部误差如何传播到 layer 与 step。

## 三、空白区

### G1. 面向真实 Ascend 多卡 MoE 的路由—tile—异构资源—通信关键路径统一模型

**反复暴露的缺口。** HyperParallel-MoE 提供真实 AIC/AIV 融合任务流，NPUMeter/AdaptCore 提供算子流水模型，DA-MoE/Weave 提供路由感知方法，TileSight 已提出从 tile 到集群的 GPU 模型。因而不能把“统一计算通信模型”本身当作无人做过的新问题。[P01、P05、P08、P03、P09、P19]

**尚未在本资料集中系统解决的组合。** 在真实 Ascend 多卡上，把原始 expert/rank 分布转成 tile 工作量与跨卡消息，再联合 AIC/AIV、MTE、共享 L2、事件等待和链路资源预测融合关键路径，并验证未见分布下的误差与选配质量。

**可检验的输出。** 同时预测总时延、各资源忙闲/等待和最慢 rank；比较峰值 roofline、串行算子求和、固定 overlap 系数与 tile/event DAG。分布、队列和竞争项做独立消融；只有总 latency 拟合不能证明机制正确。

### G2. 静态、分桶、动态策略的收益边界与决策成本统一比较

HyperParallel-MoE 测量逐 task 调度成本，DA-MoE 测 selector 成本，Analytical Resource Management 采用 launch-time 求解，Weave 做 runtime 资源适配，MPMoE 对比 profile 与 model。[P01、P03、P18、P19、P22] 各自证明一条路线可行，仍缺相同 NPU 平台、相同候选 kernel 与测量边界下的系统比较。

应建立随 token、skew、EP、图/形状稳定性变化的策略图，允许“不适配”或回退，而不是固定认定动态一定优于静态。需区分 histogram 采集、模型求解、查表、同步和代码切换成本。

### G3. 并发竞争的可组合建模与跨配置迁移

UniEP 明确承认 cache contention 未充分捕获；MDM 表明队列/MSHR 机制缺失会造成严重偏差；MPMoE 表明不同操作虽用不同硬件也会互相影响；TileSight 承认 uniform tile-rate 与部分 topology 抽象存在限制。[P02 §6.2；P14 §III；P22 §IV；P09 §7]

缺口不在于“没有人建模 contention”，而在于可否以少量微基准构建 Ascend 融合算子的可组合竞争模型，并在新 tile、核组与流量配置上泛化。应分别测通信、GMM、向量独占/两两并发/三者并发，验证参数能否复用，避免每种组合重新拟合一个黑盒系数。

### G4. 从分布摘要到真实通信拓扑与 tile 长尾的误差控制

DA-MoE 的 effective experts 与排序分布有用，但 DeepSeek-V3 的 512-token 桶存在约 20% 的 oracle gap；SimAI 使用均衡近似；Piper、UEP 和 Weave 表明 topology、慢 rank 和网络控制同样重要。[P03 §V-B；P17 §3.4；P21 §V–VI；P29 §6；P19 §3]

由此推导的待验证问题是：**相同总 token、相同 effective experts，甚至相同排序 histogram，是否因专家到 rank/链路的映射不同而需要不同 schedule？** 这是本次综合提出的假设，不能写成上述论文已共同证明的结论。可用固定分布、置换 expert placement 的成对实验，把表示损失与模型误差分开。

### G5. 跨 NPU、芯片代际和编译器版本迁移的代价与可信范围

LENS 明确把跨 NPU scaling 留给未来；NPUMeter 要重新分析流水并 profiling；AdaptCore 的模板/经验参数依赖 Ascend；AscendOptimizer 承认跨芯片/CANN/仓库转移尚待研究；CANN Bench 初始硬件和编程面也有限。[P04 §6；P08 §7；P05 §7；P06 App.C；P07 §4]

目前缺少统一回答：哪些是结构性模型可保留，哪些吞吐/时延参数必须重测，哪些调度/编译行为无法用规格缩放。需要按可获得的不同芯片或 CANN 版本做留出验证，报告迁移误差随校准预算变化的曲线；不预设一定能取得某一指定代际硬件。

### G6. 小 batch decode、跨节点、真实路由和生产干扰的联合验证

Weave 限于 4×H100 单节点 EP4；Analytical Resource Management 把新 GPU、多节点和 decode 列入未来；SwiftEP 端到端主要看 prefill；LENS 当前为 offline serving；INC-MoE 使用交换机 emulator；DynaNDE 仅模拟单 NDP。[P19 §7；P18 §VI；P28 §8.4；P04 §6；P26 §5；P20 §6]

这批工作没有共同完成“真实 Ascend、多节点、动态路由、小 batch decode、排队/并发干扰”的综合验证。应分阶段扩大：算子隔离微基准→单节点多卡→真实路由 MoE layer→训练 step 或在线请求。训练与推理分别评估，不能用 prefill ITPS 替代 decode TBT/p99。

### G7. 训练反向、低精度和确定性的联合设计

FlashMoE 明确尚需训练支持；SwiftEP 指出训练保存激活使 buffer reuse 不能直接沿用；AdaptCore 提到 FP8/INT4、稀疏与复杂融合导致瓶颈变化；CANN Bench 也将更多低精度格式列为扩展；UniEP 强调确定性 token 顺序，而 HyperParallel-MoE 已覆盖部分反向任务流。[P24 §5；P28 §9；P05 §7；P07 §4；P02 §3、6.3；P01 §4–5]

缺口不是“所有工作都没做 backward”，而是**同一性能模型/优化器**能否覆盖前反向不同依赖、激活生命周期、格式转换、梯度归约顺序和精度约束。需将 correctness tolerance 或 bitwise 目标写成优化约束，并报告峰值 buffer 内存；不能为追求重叠改变数学语义后仍称同等实现。

### G8. 模型指导优化的诊断能力、失效检测与长期维护

SynPerf 将扩展复杂分布式 EP 和自动优化列入 future work，并承认调参后仍有 residual gap；FlashMoE 提到手写融合复杂度，TileLink 提供抽象但后端受限；AscendOptimizer/CANN Bench 表明正确性、测试覆盖、基线版本同样是优化闭环的一部分。[P16 §VII、IX；P24 §5；P27 §7.4；P06 App.C；P07 §4]

仍需检验模型是否不仅能给时延，还能区分“参数未调好、候选 kernel 缺失、编译器/资源模型失配”，并在分布漂移后触发校准或回退。建议同时报告 latency error、near-oracle regret、被模型剪掉的真正最优配置比例、离线/在线成本，以及相对强基线的稳定收益。

### 与当前课题最直接的收敛点

从本资料集出发，优先级最高的是 **G1 + G2 + G3**：以真实 Ascend 的合法 tile/event taskflow 为基础，建立路由感知的异构资源关键路径模型，再用模型选择切分、任务顺序和资源配比，并测出适配净收益的边界。G4 是区分普通 shape-aware 模型的关键实验；G5–G8 可作为泛化和系统验证层逐步扩展。这里是基于文献证据提出的研究切口，尚需与完整领域检索和实际硬件条件共同确认新颖性。

> Congestion control with CPU proxy.We observe that the number of outstanding requests can have a significant impact on various NICs, affecting tail latency [46, 66]. Software-based flow control is challenging to implement with IBGDA, as GPU threads typically are not flexible enough for implementing network-level policies. **Limitations and future work（作者原文）** · `8 Discussion and Related Works — Compatibility with other large-scale training techniques` · PDF 第 11 页

> While Lancet is evaluated with data and expert parallelism, the techniques are in principle compatible with most other commonly used training optimizations. Weight gradient scheduling only utilizes operator dependency during backward propagation, thus unaffected by most distributed training sharding techniques. Some techniques introduce extra communication which may interfere with partition-based all-to-all overlapping. FSDP/ZeRO3 (Rajbhandari et al., 2020) inserts additional all-gather communication in the forward passes, which may require additional scheduling to avoid interference with overlapped all-to-all. Tensor parallelism (Shoeybi et al., 2019) requires all-reduce communication after self-attention; Ring-attention (sequence parallelism) (Liu et al., 2023) communicates the key-value blocks during the attention process. If different devices or communication channels are used for expert and tensor/sequence parallelism (e.g., inter-node vs. intra-node), the overlapped all-to-all communication can be arranged to execute concurrently with tensor/sequence parallelism traffic. Investigating the efficient orchestration and overlapping of communication arising from various sharding techniques, particularly the intricate patterns generated by automatic sharding (Zheng et al., 2022), remains future work.

**Limitation / extension（作者原文）** · `8 Discussion and Related Works — Optimizing irregular communication and expert computation` · PDF 第 11 页

> Optimizing irregular communication and expert computation Lancet’s partition produces irregular-shaped allto-alls and expert computation. While we use a simple NCCL based implementation (Fig. 10), better communication implementations targeting such dynamic workload may further improve the performance. Similarly, the shape irregularity in expert computation may cause extra computation due to padding. Block-sparse expert kernels (e.g., MegaBlocks (Gale et al., 2023)) can be further applied to accelerate the computation.
