# 性能模型与资源调度：逐篇阅读笔记

本组包含 5 篇直接相关或可迁移的 MoE 性能建模/资源管理工作。GPU 实测、NPU/NDP 模拟结果和系统级训练结果分别标注；其中除 DynaNDE 的周期级模拟外，其余工作均以 NVIDIA GPU 平台为主，不能视为 Ascend NPU 实测。

## 1. Analytical Resource Management for Fine-grained MoE Computation-Communication Overlap

**文件与定位**：`Analytical_Resource_Management_MoE_2609.07536.pdf`；arXiv 2609.07536v1，2026。面向 COMET 的 post-router MoE fused overlap 资源管理。原文重点：Sec. II–IV、Fig. 1–6、Tables III–V。

### 研究背景与 Motivation

MoE 的分布式推理需要在专家 GEMM 与 token dispatch/combine 之间隐藏通信。细粒度实现让通信 CTA 在部分 GEMM 结果 ready 后即可处理，但 compute CTA 与 communication CTA 同时争用有限 SM residency。通信 CTA 过少会留下通信尾波，过多则压缩 GEMM 并行度。路由后的 tile 数、shape、split 数改变时，最优分配也会改变；离散 CTA wave 使延迟相对资源分配呈阶梯变化，固定资源比例和逐 workload 实测查表都不理想（Sec. I–II）。

### Insight → Design

- **Insight：决定 overlap 的是依赖约束下的整体 makespan，而非单边吞吐。** 将问题建模为 dependency-constrained resource partitioning；按 routed tile 数和 split-ready 依赖计算通信何时可启动，并计入 CTA residency 的整数 wave 效应（Sec. II–III）。
- **Insight：通信和计算之间的耦合在 launch 前可由 workload 与 occupancy 信息估计。** 在 kernel launch 前插入 launch-time analytical manager，计算通信 CTA 数 `C`、相应通信 reservation `R(C)` 和剩余计算容量 `P(C)`，不需要为候选资源配置执行 kernel 或重新编译（Sec. III，Fig. 3）。
- **Insight：分割粒度影响 readiness 和资源占用。** 以 split-level readiness graph 对齐 compute tile 与 Gather/ReduceScatter 的执行波次，再选择能降低总流水时延的 partition，而不是只追求最大通信带宽或 GEMM 并行度（Sec. III，Fig. 2）。

### 实验设计

在 4 张 NVIDIA A100-SXM4-40GB、NVLink 节点上以 BF16 测试，软件为 PyTorch 2.7.1、CUDA 12.6、NCCL 2.26.2、COMET A100。覆盖 Granite-3.1-1B-A400M、Qwen1.5-MoE-A2.7B、DeepSeek-V2-Lite，batch=4，sequence length 1,024–16,384；比较 TP/EP=(4,1)、(2,2)、(1,4)。使用均匀路由以及从 LMSYS-Chat-1M 原生路由中选取 p50/p90 负载，测 GEMM2+GatherRS、post-router layer 和完整模型 prefill；COMET 为主要 baseline。warm-up 20 次，算子/层每策略 ABBA 交错采样 60 次，报告最大 rank 中位延迟和 bootstrap 95% CI；另以 C=1…16 sweep 的实测最优值作 oracle。实现保持原 kernel、算术量和通信量，仅改 C/驻留分配（Sec. IV、Tables III–IV）。

### 实验结果

资源选择器相对 measured oracle 的平均 regret 为 **3.22%**、最大 **10.21%**，单独求解开销均值 **0.157 μs**（15 个 real-p90 workloads）。相对 COMET，GEMM2+GatherRS 在均匀/p50/p90 路由下跨模型的几何平均提升约 **2.81–3.09×**；post-router layer 约 **1.88–2.29×**。TP=2/EP=2 完整 prefill 的几何平均提升：Granite **1.336×**、Qwen **1.211×**、DeepSeek-V2-Lite **1.232×**，最佳点 **1.439×**（Fig. 4–6）。结果是 A100 GPU 实测；层/端到端收益低于被优化算子，原因是其余阶段没有改变。

### 对本课题的启发与边界

这是当前目录中最直接的“解析性能模型驱动的融合资源分配”参考。可将 CTA 替换为 Ascend AIC/AIV task 或核组资源，建模通信/搬运完成事件、片上资源占用及 split/tile ready 条件，并用 measured oracle regret 与在线决策开销评估模型。Ascend 的队列、事件语义、同步、DMA、UB/L1/L0 约束均需重新表征；文中 GPU occupancy 模型和 speedup 不可直接搬用。

## 2. Weave: Fine-Grained Dynamic SM Scheduling in an MoE Megakernel for Compute-Communication Overlap

**文件与定位**：`Weave_Dynamic_SM_Scheduling_2609.21483v3.pdf`；arXiv 2609.21483v3，2026。MoE 推理 megakernel 中按路由结果动态分配 SM 并安排跨层执行。原文重点：Sec. 2–5、Figs. 3–10、Table 1。

### 研究背景与 Motivation

MoE 每层路由后各 rank 的 token/expert 工作量动态变化，通信时长和 GEMM 形状也随之变化。固定通信/计算 SM 切分不能同时适配各层；仅在单层内 overlap 还会受 layer dependency 与长尾 rank 限制。作者的测量显示 dispatch 与 GEMM 吞吐对 SM 数并非线性，且瓶颈由最慢 rank 决定（Sec. 2，Figs. 3–6）。

### Insight → Design

- **Insight：路由结果一旦产生，即可构造每层实际通信量和计算量，而无需用平均负载代替。** Weave runtime 读取 per-layer routing result，以硬件校准的 bandwidth/compute throughput 曲线为输入，在每层选择通信与计算 SM partition（Sec. 3，Fig. 4）。
- **Insight：层间存在可利用的时间依赖，通信与计算应跨层共同排程。** temporal scheduler 基于路由负载和 throughput ratio 组织工作，缩短由慢 rank、dispatch/combine 和依赖造成的 pipeline tail（Sec. 3，Fig. 5）。
- **Insight：细粒度切分会反过来降低 GEMM 吞吐。** 对 GEMM tiles 采用 chunking/stealing 时显式计入 chunk 数引起的吞吐下降，避免为了通信并行度过度拆分计算（Sec. 4、Fig. 9）。

### 实验设计

单节点 4×NVIDIA H100 80GB SXM5，GPU 通过 NVLink/NVSwitch 互连，软件含 CUDA 12.9、NCCL 2.21.5、NVSHMEM 3.6.5、PyTorch 2.6。覆盖 6 个 MoE 模型及 18 组模型/序列配置，含 DSv3、Phi-3.5-MoE、Qwen3、DSv2；序列长 2k/4k/8k。与五个系统 baseline 比较 per-layer MoE latency，并以 SGLang 等实现测完整推理端到端 latency；测试 SM partition、chunk count、routing skew 和 stealing 策略的影响（Sec. 5.1、Table 1、Figs. 9–10）。

### 实验结果

论文摘要报告全部配置上平均 **2.89×** MoE-layer speedup 和 **1.33×** end-to-end 几何平均提升；正文不同 workload 的 layer speedup 为 **1.95–4.76×**。一个关键负结果是 GEMM chunk 数 K=8 时有效吞吐较不切块下降约 **27%**（Fig. 9），说明调度空间必须含 kernel 效率损失。数字均为 H100 GPU 结果，依赖 megakernel 和可动态调 SM 的 GPU 执行模型。

### 对本课题的启发与边界

可借鉴把真实路由统计、硬件实测吞吐曲线和 tile/chunk 执行效率联合进入每层性能模型，并将 rank tail 与跨层 schedule 纳入评价。Ascend 的 AIC/AIV 计算单元不是 GPU SM，且多卡通信/卡内队列机制不同；应重新拟合算子效率曲线，并把通信事件机制和计算 tile 完成粒度作为模型输入。

## 3. DynaNDE: Dynamic Near-Data Expert Scheduling for Batched MoE Inference

**文件与定位**：`DynaNDE_2609.00407.pdf`；arXiv 2609.00407v1，2026。NPU 与近存处理 NDP 协同推理，含解析层时延模型和动态专家调度。原文重点：Sec. 3–5、Figs. 7–12、Tables 2–3。

### 研究背景与 Motivation

MoE 专家参数总量常超出 NPU 内存，按需将专家权重从外存搬入 NPU 会导致数据移动成为主开销。文中 profiling 的 DeepSeek 工作负载中参数搬移占时 **88.4%**，专家计算约 11.1%（Fig. 1）。已有 NPU–NDP 方案用固定带宽比例或启发式安排专家，未共同考虑 NPU/NDP 算力异构、参数和 activation 搬运、批处理带来的专家级并发，以及已驻留专家的复用（Sec. 1–2）。

### Insight → Design

- **Insight：NPU/NDP 的专家分配是计算收益与 PMove/AMove 成本的权衡。** 解析模型分解专家计算、参数搬移、activation 搬移和 NPU–NDP overlap，按三阶段 pipeline 计算每层 makespan，并以此最小化 layer latency（Sec. 3.1，Eqs. 1–3）。
- **Insight：batch 路由使同层多个专家能够并行，平均模型不能代表调度代价。** 建模 NPU 与 NDP 的异构吞吐和每层 activated expert workload，再由运行时基于当层 expert activation 动态分配（Sec. 3.2、Sec. 4）。
- **Insight：参数已在 NPU cache 的专家再次执行时不应重复付出 PMove。** reuse-aware ranking 将 cache residency 与预期移动成本纳入调度收益，并用 prefix-scan 评估候选分配，避免指数级搜索（Sec. 4，Alg. 1）。

### 实验设计

使用基于 NeuPIMs/DRAMSim3 扩展的 cycle-accurate simulator，不是实体 NPU 测量。模拟配置为 4 个 128×128 MAC NPU systolic arrays、64 个 4×4 MAC NDP arrays、PCIe Gen4×16、512 GB/s 外存带宽；NPU expert cache 默认总专家数的 10%、LFU。评估 Switch-Base、FLAME-MoE、DeepSeek-V2-Lite，使用 DCLM 路由 traces，batch=32，同时测 prefill 和 10-token decoding；与 NPU-only、NDP-only、MoNDE、适配后的 HybriMoE 比较，保证 trace、硬件、cache 和 memory budget 相同（Sec. 5.1、Tables 2–3）。

### 实验结果

Prefill 中 DynaNDE 相对 NPU、NDP、MoNDE、HybriMoE 的跨模型平均吞吐分别为 **1.8×、2.9×、2.6×、1.1×**；decoding 分别约 **30.5×、1.1×、2.2×、1.4×**（Figs. 8–9）。论文摘要概括相对 MoNDE 的平均提升为 prefill **2.6×**、decoding **2.2×**。decoding 调度中付出 PMove 的 NPU 专家占比为 3.6%，低于 HybriMoE 的 5.3%（Fig. 10）。这些是模拟器吞吐，不是物理 NPU 实测；具体数值对 NDP 带宽/算力及专家 cache 假设敏感。

### 对本课题的启发与边界

模型分阶段列出计算、权重/activation 搬移和 overlap，且通过当前 routing trace 做调度，适合借鉴到 NPU MoE 的开销分解和 cache reuse 建模。其主要研究对象是 NPU–CXL NDP 协同与参数 offload，不是 NPU 多卡 expert-parallel All-to-All，也没有 Ascend 真实系统验证；应迁移建模方法而非性能结论。

## 4. Piper: Efficient Large-Scale MoE Training via Resource Modeling and Pipelined Hybrid Parallelism

**文件与定位**：`Piper_2605.05049.pdf`；arXiv 2605.05049v1，2026。HPC 平台上的资源模型、PP×EP 规划与 topology-aware All-to-All。原文重点：Sec. III–VIII、Figs. 1–14、Tables II–XII。

### 研究背景与 Motivation

大规模 MoE training 同时受模型/activation 内存、EP All-to-All、专家负载不均和 fine-grained expert skinny GEMM 利用率限制。HPC 网络还可能跨节点、机柜有非均匀链路，平面 collective 会放大慢链路和拥塞。单一并行策略无法在内存可行、计算效率和网络成本之间做平台相关取舍（Sec. I–II）。

### Insight → Design

- **Insight：并行策略应先通过内存、计算、通信模型筛除不可行配置，再按平台性能排名。** Piper 用测得的平台带宽/吞吐参数化资源模型，搜索 pipeline parallel degree PP 与 expert parallel degree EP（Sec. III–IV，Fig. 1）。
- **Insight：在 MoE 层内加入 pipeline 可以限制 EP 通信组规模。** 将 P GPUs 组织为 PP×EP 网格，以 1F1B 在层/微批次间流水，把昂贵 All-to-All 限定在局部 EP group（Sec. III，Fig. 2）。
- **Insight：Dragonfly 网络层级和异步依赖决定合适的 collective。** HALO 分阶段组织 local、group/intra-rack、remote 流量，并按拓扑聚合通信、使 NIC 均匀饱和（Sec. V，Figs. 6–8）。
- **Insight：routing 偏斜导致设备负载不均，静态 expert placement 难长期平衡。** 周期性迁移同层专家，在负载收益与迁移开销间权衡（Sec. VI）。

### 实验设计

基于 Frontier AMD MI250X GPU 和 Dragonfly 网络，以 microbenchmark、代码插桩、硬件 profiling 校准模型；与 DeepSpeed-TED、DeepSpeed-MoE、X-MoE、Tutel 等比较。实验含小/中/大规模 MoE layer throughput、完整模型训练、HALO 对 RCCL all-to-all、专家迁移开销和弱扩展；报告不同 PP/EP、模型规模、节点数与 MFU。HALO 单独跨多节点/消息尺寸比较延迟；训练吞吐由完整训练运行实测（Sec. IV、VII）。

### 实验结果

论文报告 Piper 训练 MFU 相对 X-MoE 约 **2–3.6×**（摘要以 2–3.5× 概括）；HALO 在 16 节点及以上相对 RCCL 延迟降低 **1.1–9×**，小规模单交换域差距较小（Fig. 8）。系统在 512 MI250X GPU 上训练 862B 参数模型、约 39.38 TFLOPS；1024 GPU 上训练 1.7T 参数模型、约 33 TFLOPS，64→1024 GPU 弱扩展效率 73%（Fig. 14）。模型和吞吐证据来自 AMD GPU/HPC training，不是推理 fused operator 或 NPU 测量。

### 对本课题的启发与边界

适用于构建上层资源模型的变量清单：参数/activation 内存、routing 引起的负载差异、拓扑链路参数、并行度和 pipeline granularity；也提示将微基准与硬件 profiling 用作模型校准。其核心是训练期 PP×EP 和 HPC topology，不是 tile-level 单算子 overlap；Ascend 场景需换成真实 AIC/AIV、HCCS/网络带宽及 CANN runtime 参数。

## 5. MPMoE: Memory Efficient MoE for Pre-Trained Models With Adaptive Pipeline Parallelism

**文件与定位**：`MPMoE_TPDS_2024.pdf`；IEEE TPDS 35(6)，2024。MoE training 的微批次 pipeline、内存复用及 pipeline granularity/strategy 选择。原文重点：Sec. III–V、Figs. 4–17、Tables II–VI。

### 研究背景与 Motivation

MoE expert-parallel 数据流的 dispatch→expert compute→combine 中通信与计算交替，串行执行造成设备空闲；切分微批次可 overlap，但太粗 overlap 不足、太细会增加 launch 并降低 GPU/网络利用率。pipeline 还会增加 activation 与临时 buffer 的峰值，产生“memory bubbles”。pipeline 粒度与反向恢复激活的内存复用策略之间存在联合权衡（Sec. II–IV）。

### Insight → Design

- **Insight：MoE 的 dispatch、expert compute、combine 是可跨 micro-batch 交叠的阶段。** 沿 token batch 维拆分微批次，在不同 micro-batch 间交替执行两次 All-to-All 与 expert compute；相比按节点拆分，batch 维切分保留跨所有 worker 的 NCCL All-to-All 并提供更细粒度选择（Sec. III-B，Figs. 4–5）。
- **Insight：流水中不同时刻活跃的分区无需始终占有独立 buffer。** 复用 partition activation/temporary buffers，反向通过 CPU offload、重新通信或重计算等四种策略恢复必要数据（Sec. III-C，Figs. 6–7，Table II）。
- **Insight：最优 pipeline 粒度依赖 token batch，最优恢复策略还依赖网络与负载。** 联合搜索 `(n,S)`；提供 profile-based 和解析性能模型路径，并以 batch 区间与近似单峰搜索减少试探（Sec. IV，Alg. 1）。

### 实验设计

真实 GPU 集群实验：8 台 DGX A100（64×A100 40GB，200 Gbps HDR InfiniBand）与 4 节点 V100 集群（16×V100 16GiB，56 Gbps HDR）；PyTorch 1.9/CUDA 11.1/NCCL 2.7。以 BERT/GPT MoE 配置和随机 token 数据覆盖 expert size、batch、pipeline 分区数；比较 FastMoE、FasterMoE 与 profile/model 版本；测训练时长、peak memory、通信 microbenchmark、pipeline granularity sensitivity、恢复策略、profile overhead 与多节点扩展（Sec. V、Figs. 10–17）。

### 实验结果

相对 FasterMoE，MPMoE-pb/pm 平均训练加速 **1.66×/1.55×**；相对 FastMoE 为 **2.34×/2.20×**（Fig. 10）。内存相对 PMoE 在 n=2/4/8 时平均下降 **23%/34%/38%**，相对 FastMoE/FasterMoE 最多下降 **53%**；实测达到理论内存节省约 **95%**（Figs. 11–12）。8 节点扩展吞吐达到单节点 **5.76×**、约理想扩展的 72%（Fig. 17）。对 Adira 上网络波动更敏感时，profile 版本优于模型版；作者报告 model 方案在该集群受预测准确性影响。结果是较早期 NVIDIA GPU 训练系统，不代表 NPU 推理融合效果。

### 对本课题的启发与边界

可借鉴对微批/tile 粒度做成本权衡、对临时 buffer 生命周期和 memory footprint 做显式建模，以及对 online profile 代价与模型误差共同评估。需要将 training 的微批调度映射为推理 fused operator 的 tile/event 调度；GPU CUDA stream、NCCL 和跨节点模型均与 Ascend CANN/AIC/AIV 不同。文中的 memory reuse 主要优化训练激活峰值，不等同于算子级通信融合。
